# Invoice database foundation

Migration: `20260911120000_create_invoices.sql`. Local database only until approved.
No UI, payment ledger, generation automation, delivery, PDF, Services, or hosted type generation is included.

## Invoices: complete column inventory

All columns are non-null unless marked nullable. UUIDs default to `gen_random_uuid()`.

| Columns | Type / behavior |
|---|---|
| `id` | UUID primary key |
| `invoice_number` | Integer, unique GENERATED ALWAYS identity, starts at 1001 |
| `customer_id` | UUID, restrictive customer FK, immutable |
| `company_name_snapshot` | Nonblank text |
| `primary_contact_name_snapshot`, `email_snapshot`, `phone_snapshot` | Nullable text |
| `billing_address_line1_snapshot`, `billing_address_line2_snapshot` | Nullable text |
| `billing_city_snapshot`, `billing_state_snapshot`, `billing_postal_code_snapshot`, `billing_country_snapshot` | Nullable text |
| `issue_date` | Finite date; default current America/New_York business date |
| `due_date` | Finite date, >= issue date; defaults on insert to issue date + captured payment terms |
| `payment_terms_days_snapshot` | Nonnegative integer |
| `status` | Text: draft (default), sent, void |
| `notes`, `terms` | Nullable customer-facing text snapshots |
| `sent_at` | Nullable finite timestamptz; database assigned when issued |
| `voided_at`, `void_reason` | Nullable timestamptz/text; required together for void; reason nonblank |
| `created_at`, `updated_at` | Finite timestamptz, default now; updated >= created |

Customer fields and default payment terms are captured by the insert trigger, not trusted from the caller. An explicitly supplied valid due date is allowed. Draft snapshots can be corrected deliberately; customer edits never refresh them automatically. After issue, display and financial fields are immutable. Number, customer, UUID, and creation timestamp cannot change even in draft.

Identity numbering is concurrency-safe and may have gaps after failures/rollbacks. There is no `max + 1`, application number assignment, prefix, or sequence reset privilege. Integer capacity is sufficient for this single-user business.

## Invoice items: complete column inventory

| Column | Type / behavior |
|---|---|
| `id` | UUID primary key, generated by default |
| `invoice_id` | Required UUID, restrictive invoice FK |
| `position` | Positive integer; unique within invoice, deferrable for reordering |
| `description` | Required nonblank text snapshot |
| `source_type` | Required text: manual (default), retainer_fee, hourly_time, retainer_overage |
| `quantity` | Required positive numeric(20,8); time quantities calculated from minutes |
| `unit` | Required text: hour, minute, flat, each, mile, month, custom |
| `unit_rate` | Required nonnegative numeric(12,2); time lines use an hourly rate |
| `billed_minutes` | Nullable positive bigint; required only for hourly_time/retainer_overage |
| `amount` | Required generated numeric(24,2) |
| `tax_amount` | Required nonnegative numeric(24,2), default zero |
| `billing_agreement_id` | Nullable UUID, restrictive agreement FK; required for fee/overage |
| `period_start`, `period_end` | Nullable finite dates; required for fee/overage, exclusive end > start |
| `released_at` | Nullable finite timestamptz, only assigned by voiding the parent |
| `created_at`, `updated_at` | Required finite timestamptz, default now; updated >= created |

Manual lines have no agreement or period and need no time source. Retainer-fee lines require quantity 1 and unit month; the database captures the agreement's monthly fee. The agreement must belong to the invoice customer, and its period must be a complete agreement-specific calendar period, clipped to that version's effective dates. Historical/disabled agreements can be invoiced; this does not re-resolve time entries.

Manual/fee amounts are `round(quantity * unit_rate, 2)`. Time amounts are `round(billed_minutes * unit_rate / 60, 2)` using numeric arithmetic. Hours displayed to eight decimal places do not drive financial arithmetic. Negative/NaN values are rejected; fixed numeric precision also rejects infinity/overflow. Quantity must be positive, while zero rate is valid.

Tax is an explicit cent snapshot, not a computed tax rate or tax engine. A later tax model can populate/extend this without replacing lines. Currency is documented as USD rather than introducing unimplemented multi-currency behavior.

## Source claims and time allocations

`invoice_time_allocations` columns:

- UUID `id` primary key, default generated UUID.
- Required restrictive UUID FKs `invoice_item_id`, `time_entry_id`.
- Required bigint `minute_start >= 0`, `minute_end > minute_start`.
- Generated bigint `allocated_minutes = minute_end - minute_start`.
- Nullable finite `released_at`, assigned only through parent invoice voiding.
- Required finite `created_at`, default now.

Offsets are zero-based positions within **rounded** billable minutes, not timestamps or actual elapsed-minute offsets. For a 30-minute entry with 15 included minutes, `[15,30)` records its 15 overage minutes. One line can collect many entries; one entry can contribute disjoint ranges to multiple lines. No per-allocation dollar amount is rounded: the aggregate invoice line owns cents.

The insert trigger verifies customer, billability, non-void source, bounds, line type and captured hourly rate. Hourly lines accept only non-retainer entries. Overage lines require the captured agreement, the usage RPC's period, and minute ranges wholly outside the included portion returned by that unchanged RPC. The entry is touched/locked while validating to prevent concurrent source corrections. Allocation totals cannot exceed the line's planned minutes, and issuing requires exact equality.

Two partial GiST exclusion constraints provide concurrency-safe active claims:

- Fee items: same agreement cannot claim overlapping `[period_start,period_end)` ranges.
- Time allocations: same entry cannot claim overlapping `[minute_start,minute_end)` ranges.

Both apply when `released_at IS NULL`, including drafts, so drafts reserve sources. The existing btree_gist extension is reused. Fee and time claims survive as historical rows when released.

A partial unique index, `invoice_items_retainer_overage_once_idx`, additionally permits only one active retainer-overage line for `(billing_agreement_id, period_start, period_end)`. It applies across invoices and within the same invoice, including drafts. Released/voided lines do not reserve the period. The initial generator must put the complete authoritative period overage charge on that one line; it must not split a period across active invoices. This does not restrict disjoint partial allocations of non-retainer hourly time. The uniqueness index enforces claim cardinality; the future atomic generator must select the complete usage result rather than a subset.

Time entries with **any** allocation history cannot be edited, voided, or deleted, including after invoice voiding. Entries with no invoice linkage retain existing behavior. This intentionally favors audit preservation; any future source-correction facility must be explicit and transactional.

## Lifecycle, totals, and transactions

Supported transitions: `draft -> sent -> void` or `draft -> void`. No reopening, paid boolean, stored overdue, hard deletion, or payment timestamp is introduced. `sent` means issued/finalized in this database foundation; it does not assert that an email was delivered. Payment-derived paid/part-paid/overdue display belongs with the future payment ledger and remaining-balance query.

Draft manual/unallocated lines can be updated. Once a time line has source allocations, it is immutable even in draft; correct it by voiding and replacing the draft. This foundation deliberately does not add source-release/edit RPCs or DELETE privileges. Issued lines are immutable except their internal release timestamp.

`invoice_totals` is a security-invoker view: invoice_id, subtotal, tax_amount, total. Totals sum stored generated cent amounts and explicit tax. Empty drafts return zero. Issued totals remain stable because issued line sets and amounts cannot change. Void invoices retain their original totals; future receivables must exclude void records.

Voiding assigns a server timestamp and requires a reason. In the same transaction, an AFTER trigger releases item and time claims, allowing rebilling while retaining all old rows, references and amounts. A failure rolls the whole operation back.

Each child write updates/locks its invoice row, so a concurrent issue or void cannot omit an in-flight child write. A real parent row version also makes a stale REPEATABLE READ writer retry. Source locks similarly protect concurrent edits to time. Deadlocks/serialization failures must be retried by future transaction callers.

The follow-up `20260912120000_create_manual_invoice_rpc.sql` adds atomic, idempotent manual draft creation; see [the RPC contract](manual-invoice-rpc.md). Automated source generation and draft editing remain separate future work. A future source-generation RPC should insert header, lines and claims and optionally issue in **one transaction**, validate caller auth, use a request idempotency key, and return authoritative totals. Protected drafts can exist while incomplete; they cannot be issued with missing time allocations. This is not permission to implement financial creation as fragile independent network writes.

## Unbilled view and usage boundaries

`unbilled_time_entries` retains its old columns and appends bigint `invoiced_minutes` and `uninvoiced_minutes`. It excludes fully claimed live billable entries and keeps partial rows with their remaining minutes. Draft reservations count; released claims do not. It remains read-only and `security_invoker = true`.

**Unclaimed retainer minutes are not necessarily chargeable minutes.** They include covered allowance. The future generator must intersect unclaimed ranges with the governing usage RPC's overage allocations, never invoice the view's remaining number as a quote. The usage engine is unchanged and continues to include invoiced work in allowance consumption.

Nexa does not automatically prorate either included hours or fixed retainer fees. Each agreement-specific period receives the full configured allowance and full monthly fee, including shortened first/last periods. For a September 8 start, billing day 1, $500 monthly fee and one included hour, September 8–October 1 receives $500 and the full hour. Versions are never combined into one allowance pool. A deliberate reduction will require a future explicit adjustment, not a day/percentage calculation.

## Backdated work, released history, and future adjustments

Finalized invoices are historical. New/backdated entries do not mutate their header, lines, amounts, totals or allocations. New entries have no claims and remain visible as uninvoiced. Non-retainer work can be claimed by a future invoice through the existing hourly linkage.

For retainer work in a period with an active finalized overage claim, the one-period-claim policy blocks a second overage claim even when late entries remain uninvoiced. A future workflow must explicitly void/rebill the complete period, or introduce an approved separate adjustment mechanism; it must not disguise the work as a different period or hourly/manual source to bypass the restriction. No new correction/adjustment workflow is implemented here. The live usage RPC can reflect later work while the original invoice snapshots stay unchanged.

Voiding preserves invoice, line and allocation history and releases reservations. It never unlocks the original time entry's billing context. The current design is stricter: all historically linked time remains protected against edits/voids/deletes, even after release. Correcting an erroneous linked source will require a dedicated historical correction operation; it cannot be done by rewriting snapshots or by the ordinary unlinked-entry soft-void path.

Current positive quantity and nonnegative rate/tax constraints intentionally reject negative discount or credit lines. A future migration can introduce a constrained adjustment source type with signed amount rules, or a separate credit/adjustment structure, without replacing the invoice/source model. The totals view already uses signed-capable numeric sums. No negative-line support is enabled in this step.

Future generation must still validate complete current period quotations atomically, including stale draft quotations after backdated work. The single-claim index does not calculate completeness or close a usage period. Payment ledger allocations, refunds/credits and balance-derived status remain future work; do not add a manual paid flag or void paid invoices without payment reversal rules.

## Security, objects and indexes

All three tables have RLS with authenticated SELECT/INSERT/UPDATE policies. Explicit revokes remove PUBLIC/anon/authenticated defaults first. Authenticated receives only SELECT/INSERT/UPDATE; no DELETE/TRUNCATE/REFERENCES/TRIGGER. Views receive authenticated SELECT only. No anon access, service-role changes or security-definer RPCs. All five new functions are invoker trigger helpers with direct EXECUTE revoked. Identity sequence access is not granted directly.

Functions: `guard_invoice`, `guard_invoice_item`, `guard_invoice_allocation`, `protect_invoiced_time`, `release_void_invoice_sources`. Existing `set_updated_at` is reused on invoices/items. Existing `get_retainer_period_usage` is called, not modified. One identity-owned sequence: `invoices_invoice_number_seq`.

Indexes beyond primary/unique/exclusion indexes:

- Invoices: customer + issue_date; issue_date; sent due_date partial index.
- Items: active agreement/period overage unique index; agreement FK partial index; invoice/position uniqueness already supports parent lookups.
- Allocations: item FK; time-entry FK including released history (the active exclusion index does not cover released rows).

Every new FK uses ON UPDATE RESTRICT / ON DELETE RESTRICT. There are no cascades. Customer, agreement and time identity changes cannot orphan invoice history.
